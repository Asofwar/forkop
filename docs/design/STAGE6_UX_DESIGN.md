# Stage 6 — Forkop UX/UI + Autotune productization: Design Report

Статус: **дизайн на утверждение. Реализация UI не начиналась.**
Ветка: `feature/observability-safety-ux`, база — коммит `67ab02e` (Stage 5).

---

## 0. Исходные условия и зафиксированные ограничения

### 0.1 Итог Stage 5

Stage 5 принят.

**REAL PRODUCTION APPLY = NOT TESTABLE**, пока не появится реальная цель, для которой одновременно выполняется всё:

- direct действительно не работает или нестабилен;
- Stage 4 выбирает non-direct кандидата;
- цель уже принадлежит корректному production DPI rule.

Искусственное production DPI rule ради hardware apply test не создаётся, сценарий не форсируется.

### 0.2 Архитектурное ограничение (обязательно для всего Stage 6)

1. В Forkop **нет per-target DPI strategy**. DPI-стратегия — это `nfqws_opt` целого правила (UCI `section` с `action=zapret`). Цель попадает в правило через его matchers, а sing-box применяет правила по принципу «первое совпадение».
2. Stage 5 (`autotune/apply.uc`) безопасно меняет **только strategy существующего DPI rule/group**. Изменение действует на всю группу целей правила, и план явно называет эту группу (`scope`).
3. `direct` **никогда** автоматически:
   - не отключает DPI глобально;
   - не создаёт и не удаляет правила;
   - не переносит цель между routing groups.

   Если цель стоит в DPI-правиле, результат `direct` — это `direct_not_applicable`. Если DPI-правила нет — `no_change_required`.
4. Следствие для UX: **единица применения — группа (правило), а не отдельная цель.** UI Autotune обязан показывать группу как главный объект, а цели внутри неё — как источники измерений. Иначе пользователь будет ждать per-site стратегию, которой нет.

### 0.3 Метод аудита и его пределы

- **Что анализировалось.** Весь frontend (`fe-app-forkop/src`, `luci-app-forkop/htdocs/.../view/forkop/*.js`), ACL, menu, po-файлы, backend-команды, которые использует UI (`forkop/files/usr/bin/forkop`, `usr/lib/**`), и тесты-контракты.
- **Как проверялись выводы.** Инвентаризацию по вкладкам собирали вспомогательные агенты (не reviewer'ы). Каждый ключевой вывод затем перепроверен вручную по коду, ссылки на строки приведены ниже.
- **Доступа к роутеру из облачного контейнера нет.** Живых скриншотов и real Monitoring data в этом аудите нет. Responsive-выводы сделаны по CSS: breakpoints, min-width, nowrap, фиксированные колонки.
- **Mutating-операций не было.** Production config не менялся.
- **Что нужно сделать на железе.** На этапе реализации каждый stage проверяется на роутере read-only браузером на 1440 / 1024 / 768, RU-локаль, роли admin и read-only (см. K).

```

 └─ form.Map "forkop", tabbed=true    (forkop.js:304-479)

 └─ form.JSONMap: Дашборд, Диагностика   (Мониторинг/Компоненты/Секции/Настройки не рендерятся)
```

Общие механизмы:

- **Save & Apply hook** (`forkop.js:306-402`):
  1. `snapshotCreate("automatic")`;
  2. подтверждение reload через `get_health_status`;
  3. toast с сырым diff `section.option: before → after`.
- **Footer LuCI «Сохранить / Применить / Сбросить»** один на всю Map и **виден на всех вкладках**, включая Dashboard, Monitoring, Diagnostics и Components.
- **Межвкладочная навигация** — программный click по `[data-tab=…] > a` (`health.ts:60`, `routeDebugger.ts:87`, `renderCheckSection.ts:40`). URL-deep-links нет.
- **Глобальные поллеры:**
  - `get_ui_state` — 1 с в покое, 0.5 с во время действий (`runtimeUiState.service.ts:6-8`);
  - log watcher `check_logs` — 10 с, LuCI-уведомления о новых версиях и ошибках (`core.service.ts`).
- **Тосты** — собственный `.toast` (жёсткие цвета `#28a745` / `#dc3545`, `styles.ts`) плюс `ui.addNotification`: две системы уведомлений.

### A.2 Инвентарь по вкладкам

Обозначения:

- **RPC** — команда `/usr/bin/forkop …`, если не указано иное.
- **Мутация:** **M** — меняет конфигурацию или runtime; **R** — только чтение; **RT** — runtime-побочный эффект без изменения конфигурации.
- **Данные:** **O** — observed (наблюдается); **C** — configured (из конфигурации); **S** — simulated/calculated (расчёт).
- **RO** — поведение в read-only роли.

#### A.2.5 Секции (правила) — `section.js`

- **Grid:** имя, «Включено», «Действие», Edit/Delete, drag.
  - Сводки условий, устройств и статуса нет.
  - Метки действий **не локализованы** («Connection», «Bypass», «Block»; `section.js:3752-3817`).
- **Модалка правила** — 2 вкладки:
  - «Настройки»: 26 опций, из них 4 навсегда скрыты;
  - «Условия»: 12 опций;
  - плюс 7 типов вложенных модалок: примерно 64 поля.

  **Итого около 102 полей на правило.**
- **DPI-стратегия** — одна textarea на правило (`nfqws_opt` / `nfqws2_opt` / `byedpi_cmd_opts`) с локальным анализатором и удалённой валидацией. Per-target стратегии нет (см. 0.2).
- **Мутации** — через Save & Apply (со снимком).
- **RO:** вкладка не рендерится.

#### A.2.6 Настройки — `settings.js`

- **34 опции в одной плоской TypedSection.** DOM-хак переносит «опцию №7 и всё после неё» в `<details>` «Дополнительные настройки» (`settings.js:163-206`). Значит, «Advanced» — это не отобранная группа, а 28 из 34 опций.
- `yacd_secret_key` — обычный `Value`, **не password**.
- В самом низу — **«Снимки конфигурации»**:
  - список: `дата · kind`, где kind — manual/automatic, reason не показан, LKG не отмечен;
  - действия: Просмотреть изменения (сырой текст), Восстановить (`window.confirm`), Удалить (`window.confirm`), Создать снимок.
  - Рендерится **только если найдена строка `dns_rewrite_ttl`** (`settings.js:168`).
- **RO:** вкладка не рендерится, хотя read-ACL разрешает `config_snapshot_list` и `config_snapshot_diff` (diff маскируется в `snapshots.uc: safe_value`).

### A.3 Backend, который UI использует или должен использовать

- **Health** (`diagnostics/health.uc`):
  - уровни: `ok | warning | error | transitioning | recovered | unknown`;
  - события: `kind ∈ start | reload | restore | recovery`, `status ∈ success | failure | recovered`;
  - хранение — **10 штук в tmpfs**, теряются при перезагрузке.
- **Snapshots** (`config/snapshots.uc`):
  - `reason ∈ manual | before-reload | pre-restore | last-known-working | before-autotune`;
  - LKG-указатель `config-snapshots/last-known-working`, **но `config_snapshot_list` не отдаёт флаг `is_lkg`**;
  - retention — 10 снимков.
- **Autotune** (`autotune/*.uc`):
  - **нет CLI-подкоманды, нет UCI, нет ACL, нет UI**;
  - результаты tune не сохраняются (только stdout);
  - `/etc/forkop/autotune-apply.json` хранит только **последний** apply;
  - истории нет.
- **Route trace:** наблюдаются только `dns` и `interface`, остальное — `unknown`.
- **Статус службы:** строки `"running & enabled"` / `"stopped but enabled"` / …, или `starting` / `stopping` / `restarting` / `reloading`.

## D. Proposed navigation tree

### D.1 Решение: LuCI menu subtree вместо одной tabbed Map

**Рекомендую** заменить одну `form.Map` с вкладками на поддерево меню LuCI, где каждая страница — отдельный view:

```
admin/services/forkop                 "Forkop X"          firstchild → overview
 ├─ overview        "Обзор"            view forkop/overview       acl: luci-app-forkop
 ├─ monitoring      "Мониторинг"       view forkop/monitoring     acl: luci-app-forkop
 ├─ diagnostics     "Диагностика"      view forkop/diagnostics    acl: luci-app-forkop
 ├─ autotune        "Автоподбор DPI"   view forkop/autotune       acl: luci-app-forkop
 ├─ history         "История и восстановление"  view forkop/history  acl: luci-app-forkop
 └─ settings        "Настройки"        view forkop/settings       acl: luci-app-forkop-admin
      (внутренние вкладки Map: Правила · DNS · Сеть · Списки и обновления · Служебные · Компоненты)
```

Почему поддерево меню:

1. **Настоящие URL и deep links.** `…/forkop/diagnostics#check=site&host=youtube.com`, `…/forkop/autotune#group=<rule>`, `…/forkop/history#snapshot=<id>`.
2. **Footer Save & Apply только там, где есть форма.** Для страниц без формы `handleSave`, `handleSaveApply` и `handleReset` = `null`. Это закрывает P2-2.
3. **Read-only определяется до рендера меню.** Страница Настроек не видна ролям без `luci-app-forkop-admin`. Никаких «спрятать кнопку после рендера».
4. **Каждая страница грузит только свои данные.** Это важно на роутерах с 256 MiB.
5. **Старый URL `admin/services/forkop` продолжает работать** (firstchild).

Риски и проверки:

- Вложенный tab-menu рендерят и bootstrap, и material, и argon. **На этапе K0 проверить на реальной теме роутера.**
- Save & Apply hook со снимком нужно вынести в общий helper и подключить во view Настроек.
- **Известное ограничение (уже сейчас):** применение через глобальный индикатор «Несохранённые изменения» в шапке LuCI обходит UI-hook. Безопасность не страдает: backend делает before-reload snapshot в `lifecycle.uc:1683`. Пропадает только toast с diff. Сделать toast из истории (см. H/K).

**Альтернатива (если поддерево не подойдёт):** оставить одну Map, переставить вкладки (Обзор первым), скрывать footer на нефоромных вкладках через TabService, а deep links делать через `location.hash`. Работает, но read-only и загрузка остаются сложнее.

Тексты — русские: RU — основной стресс-тест длины.

## H. Autotune UX

### H.1 Режимы

| Режим | Что делает worker | Что видит пользователь |
|---|---|---|
| **Выключен** | ничего; ручной «Перепроверить» доступен админу | Последние результаты (если есть), помеченные «устарели, автоподбор выключен» |
| **Только рекомендации** | по расписанию меряет цели, копит гистерезис, **не применяет** | Карточки с рекомендацией и `[Применить …]` (admin) |
| **Автоматически** | то же + при выполнении политики применяет через `apply.uc` (verify + rollback) | Уведомление на Обзоре и в Истории: «Автоподбор применил…» или «…откатил» |

Переключение режима:

- segmented control на странице Автоподбора (admin);
- пишет UCI `forkop.autotune.mode` через отдельную команду `autotune_policy_set` (валидация + `uci commit`);
- **reload sing-box не нужен**, поэтому не идёт через Save & Apply;
- в RO это read-only текст.

Перед включением «Автоматически» — модалка:

> Forkop будет сам менять стратегию существующих DPI-правил, только после N подтверждений подряд, с проверкой и автоматическим откатом. Он никогда не создаёт и не удаляет правила, не отключает DPI и не переносит цели между группами.

### H.2 Список: группа → цели

- **Primary-объект — группа** (DPI-правило). В карточке: текущая стратегия, лучший вариант, уверенность, стабильность, прогресс подтверждения, время последней проверки и объяснение одной-двумя фразами.
- **Цели** — внутри группы, раскрываются.
- **Цели вне DPI-правил** — отдельный свёрнутый список с объяснением по каждой:
  - «идёт через VPN»;
  - «идёт напрямую, DPI-правила нет — обход не требуется» (`no_change_required`);
  - «правило не определяется однозначно: выше стоит удалённый список» (`rule_owner_undecidable`).
- **Конфликт в группе** (разные цели требуют разных стратегий) → рекомендации нет, с объяснением:

  > youtube.com стабилен с multisplit, i.ytimg.com — только с fake. Стратегия задаётся на всё правило, поэтому Forkop её не меняет. Можно разнести цели по разным правилам вручную.

### H.3 Объяснения (reason code → текст)

Шаблоны строятся из `select.uc` / `apply.uc` reason codes и метрик. Сырой `selected = multisplit` не показывается никогда.

| Код | Текст |
|---|---|
| `direct_stable` | «Direct работает стабильно (7 из 7). Обход DPI не требуется.» — и, если цель в DPI-правиле, дополнительно: «Цель находится в DPI-правиле «X». Forkop не отключает DPI автоматически — при желании уберите цель из правила вручную.» (`direct_not_applicable`) |
| `direct_failed_candidate_stable` | «Direct не работает (0 из 7, сбросы TLS). {cand} стабилен — рекомендован.» |
| `direct_unstable_candidate_stable` | «Direct нестабилен ({k} из {n}). {cand}{ и {others}} стабильны{; {cand} проще — поэтому выбран он}.» |
| `candidate_more_reliable_than_direct` | «{cand} надёжнее direct ({a} против {b}).» |
| `materially_faster_than_direct` / `materially_faster` | «{cand} заметно быстрее: TLS {x} мс против {y} мс.» |
| `simplest_stable` | «Несколько стратегий стабильны с сопоставимой задержкой; выбрана самая простая — {cand}.» |
| `no_stable_candidate` | «Ни одна стратегия не стабильна. Лучшая — {leading} ({k}/{n}). Текущая стратегия оставлена без изменений.» |
| `all_failed` / `target_unreachable` | «Цель недоступна ни одним способом — возможно, проблема не в DPI. Текущая стратегия оставлена без изменений. (Проверить сайт в Диагностике ›)» |
| `target_ip_mismatch` / `target_unresolved` | «Адрес цели менялся во время проверки — данных недостаточно. Текущая стратегия оставлена без изменений.» |
| `isolation_unavailable` | «Безопасная изолированная проверка сейчас невозможна (контракт маршрутизации не выполнен). Ничего не изменено.» + ▸ violations |
| `guard_active` / `snapshot_operation_in_progress` / `autotune_in_progress` | «Проверка отложена: идёт {восстановление / операция со снимком / другой прогон}.» |
| `candidate_already_active` | «Текущая стратегия уже лучшая — менять нечего.» |
| stale-коды apply (`config_changed`, `strategy_changed`, `uncommitted_uci_changes`…) | «Применение отменено: {конфигурация изменилась после проверки / есть несохранённые изменения}. Будет перепроверено.» |
| `verification_failed` → `rolled_back` | «Стратегия {cand} применена, но проверка в production не прошла ({check}). Конфигурация автоматически возвращена к снимку «Перед автоподбором».» |
| `needs_attention` | «Откат не завершился. Нужна ручная проверка. (История и восстановление ›)» |

### H.4 Confidence и stability

- **Уверенность:** «высокая / средняя / низкая» + основание мелким шрифтом: «7 из 7 проб, 3 прогона подряд».
- **Стабильность:** «стабильно (≥ 80 %) / нестабильно (≥ 50 %) / сбой» + `k / n`.
- Задержка — только медиана TLS по успешным пробам. У неудачных задержки нет («—»), это контракт `select.uc`.

### H.5 Гистерезис

```
Найдена новая стратегия: multisplit
Подтверждение: ●○○ 1 / 3
Автопереключение пока не выполнено: нужно 3 прогона подряд с тем же результатом
и уверенностью не ниже «высокой». Следующий прогон — 08:10.
```

Правила (backend, H.8) и их отражение в UI:

- **Счётчик растёт**, только если тот же кандидат выбран снова с `confidence ≥ policy.min_confidence`.
- **Другой кандидат** → счётчик сбрасывается на 1 для нового: «Результат изменился (был fake) — подтверждение начато заново».
- **`inconclusive`** не увеличивает счётчик: «Прогон не дал данных — прогресс сохранён». Два inconclusive подряд сбрасывают его: «Два прогона подряд без данных — подтверждение сброшено».
- **Изменение конфигурации правила** (hash) сбрасывает счётчик с объяснением.
- **Кандидат после отката** не применяется повторно в течение cooldown: «multisplit откатывался сегодня в 02:15 — повтор не раньше 02:15 завтра».

### H.6 История автоподбора

События: прогон (результат), рекомендация создана / подтверждена / отклонена / устарела, применение начато / применено / откат / needs_attention / отменено (stale reason), смена режима.

- Страница Автоподбора показывает последние 5, остальное — ссылкой в «Историю и восстановление» с фильтром «Автоподбор».
- Apply / rollback обязательно пишутся **своим kind** (`autotune_apply`, `autotune_rollback`), а не `restore` (исправление P1-4).

### H.7 Откат

- «Откатить последнее применение…» (⋯ группы, admin) использует `apply.uc rollback`.
- Модалка: «Вернуть стратегию группы «YouTube» fake (снимок «Перед автоподбором» от 02:13)? Будут восстановлены параметры, изменённые автоподбором.»
- Если после apply конфигурация менялась (`config_is: other`), откат блокируется с объяснением. Взамен предлагается ссылка на снимок в Истории.

### H.8 Backend concepts → UX / API / state (только дизайн, без реализации)

## I. Read-only model

**Принципы:**

1. Роль определяется **до рендера**:
   - меню по ACL-группам;
   - на странице — `accessMode` до первого `render()`.
2. Чистые мутации **не рендерятся**. Действие показывается disabled с подписью «Доступно администратору» только там, где его отсутствие само по себе сбивает с толку. Пример: «Рекомендация готова» без кнопки выглядит как баг.
3. **Никаких привилегированных вызовов из RO:**
   - WS с secret → RPC `clash_api get_connections`;
   - section-cache → пропустить;
   - `ui_action_ack` → не вызывать;
   - `global_check raw` → `masked`.
4. **Отсутствие данных из-за роли — это не ошибка.** Показывать нейтральное «Недоступно для этой роли», а не ✕.

| Страница | RO видит | RO не видит / не может | Нужные ACL / изменения |
|---|---|---|---|
| Обзор | состояние, маршрутизацию (read-only sections), автоподбор, восстановление, последнее событие | ⋯ управления службой | всё уже в read ACL, кроме истории → `forkop history` |
| Мониторинг › Соединения | соединения (RPC poll), имена устройств, пути, тип DPI-провайдера; стратегию — только если расширить allowlist (см. ниже) | закрыть соединение / все | `clash_api get_connections` уже есть; сейчас вкладка **не рендерится** — включить |
| Мониторинг › Узлы | группы, активный узел, задержки из `/proxies` | выбор узла, проверка задержки, подписки, параметры URLTest | `clash_api get_proxies` уже есть |
| Диагностика | проверки, «Проверить сайт», набор адресов (localStorage), глобальная проверка и конфиг (**masked**), логи | отчёт для поддержки (raw), песочница DPI (validate — write) | исправить `raw` → `masked` в RO |
| Автоподбор | режим (текст), группы, цели, рекомендации, гистерезис, историю, технические детали | переключение режима, перепроверку, применение, откат, отклонение | `autotune_status`, `autotune_target *` → read ACL |
| История и восстановление | состояние, ленту, снимки, diff (маскированный) | создать / восстановить / удалить | `config_snapshot_list/diff` уже есть; добавить `is_lkg` в list; `history` → read ACL |
| Настройки | — (пункт меню скрыт) | всё | menu `depends.acl: luci-app-forkop-admin` |

**Граница безопасности — DPI-стратегия в RO.** `get_readonly_config_sections` отдаёт только allowlist: `action`, `enabled`, `interface(s)`, `label`, `section`, `sort_by_latency`, `urltest_enabled`, `urltests`, `priority_groups` (`diagnostics/runtime.uc:809-825`). `nfqws_opt`, `nfqws2_opt` и `byedpi_cmd_opts` туда не входят. Значит, без изменения RO видит «DPI · zapret · правило YouTube», но не саму стратегию. Секретов в стратегиях нет: анализатор запрещает hostlist, ipset и fwmark. Всё равно это изменение read-границы — **решение за вами** (п. 7 в конце). Autotune-статус для RO показывает имена кандидатов (multisplit и т. п.), а не сырые `nfqws_opt`: сырые строки идут только в «Технических деталях» и только для admin.

Тест-контракт: расширить `tests/luci_readonly_view.sh` и `tests/acl_boundary.sh` на новые страницы. Для каждой RO-страницы — список разрешённых RPC и «ноль mutating-вызовов при рендере».

## J. Unified component design

### J.1 Status

Семантическая модель frontend (одна для всех страниц):

| Семантика | Тон | Иконка | RU-подпись по умолчанию | Сюда отображаются текущие значения |
|---|---|---|---|---|
| `healthy` | success | ● | Норма | ok, success, running, reachable, latest, stable, applied, confirmed, created, deleted |
| `warning` | warning | ▲ | Внимание | warning, unstable, timeout, outdated, dev, recovered (как итог — «Восстановлено»), rolled_back |
| `error` | error | ✕ | Ошибка | error, failure, failed, stopped (если ожидался запуск), unreachable, dns_failed … |
| `needs_attention` | error + действие | ⚠ | Требуется действие | needs_attention, guard active + recovery pending, package_pending |
| `busy` | info | ◌ (spinner) | Выполняется… | loading, checking, running (job), transitioning, starting / stopping / restarting / reloading, verifying, rolling_back |
| `not_checked` | neutral | ○ | Не проверено | skipped, not_run, pending, idle, unknown-из-за-отсутствия-проверки |
| `unsupported` | muted | ⊘ | Не поддерживается | unsupported, not_applicable, direct_not_applicable, `udp_fake` / `ipfrag` |
| `off` | muted | — | Выключено | disabled, not installed, inactive, mode=off |
| `unknown` | neutral | ? | Нет данных | только когда источник **ответил**, но значение неизвестно (не путать с not_checked) |

Отдельный словарь **исходов событий** для истории: `succeeded`, `recovered`, `rolled_back`, `failed`, `needs_attention`, `cancelled` (stale / refused).

Реализация:

- **`status.ts` — единственный модуль**: `toSemantic(domain, raw)` + `label(semantic, context?)` + `tone(semantic)`. Все подписи — через `_()` в одном месте.
- Удаляются локальные словари `health.ts: statusLabel`, `statusLabels.ts: checkStatus / eventStatus / healthStatus`, строки `'✔ Running'`.
- Контекстные подписи разрешены, например «Подключено» вместо «Норма» для узла. Семантика и цвет при этом те же.

**Provenance chip** (обязателен везде, где показывается маршрут или стратегия):

- `observed` → «наблюдается»;
- `configured` → «из конфигурации»;
- `simulated` → «расчёт»;
- `unknown` → «не определено».

### J.3 Action

| Тип | Вид | Когда |
|---|---|---|
| primary | `cbi-button-action` (акцент) | одно главное действие страницы или карточки |
| secondary | `cbi-button` | 1–2 частых действия |
| destructive | текст красный, **всегда модалка подтверждения** с последствиями | Остановить, Удалить, Восстановить, Закрыть все, Полное удаление, Откатить |
| icon | 28×28, `aria-label` + `title` обязательны | повтор отдельной строки, копировать, закрыть панель |
| overflow `⋯` | меню | редкие действия, всё деструктивное в строках таблиц |

Правила:

- В строке таблицы **максимум одна видимая кнопка + ⋯**.
- Кнопка во время операции → `busy` со спиннером и текстом «Выполняется…». Остальные действия того же объекта disabled с `title`, объясняющим причину.
- Результат **всегда** виден: toast для кратких, inline-статус для длинных. `logger.error` без UI запрещён.
- Замена `window.confirm` → общая модалка `confirmAction({title, consequences, confirmLabel, danger})`.

Аудит текущих кнопок → новая роль:

| Текущее | Новое |
|---|---|
| 9 кнопок «Доступных действий» | Обзор: `[Запустить]` (только когда остановлен), ⋯ (Перезапустить, Остановить…, Автозапуск); Диагностика › Технические данные: 4 secondary |
| Обновить подписки / Проверить задержку / 3 ссылки (Dashboard) | Узлы: secondary «Проверить задержку», остальное в ⋯ |
| Детали / Trace / Копировать / Закрыть (строка соединения) | ⋯ (Подробнее — по клику на строку) |
| Проверить обновление / Обновить / Удалить (компонент) | primary «Обновить» (если есть обновление), иначе secondary «Проверить»; «Удалить…» — в ⋯ |
| Повторить / Открыть настройки / Копировать (карточка проверки) | secondary по контексту (одна) + «Повторить эту проверку» (icon) + ⋯ |
| Просмотреть / Восстановить / Удалить (снимок) | secondary «Изменения», ⋯ (Восстановить…, Удалить…) |

### J.4 Empty state

`EmptyState { icon, title, hint?, action? }`. Контекстные тексты:

- «Нет активных соединений» / «Нет закрытых соединений за эту сессию»
- «Ничего не найдено по фильтру» + (Сбросить фильтры) — **отличается** от «нет данных»
- «Проверка ещё не запускалась» + [Запустить проверку]
- «Снимки ещё не создавались» + (Создать снимок)
- «Истории пока нет — события появятся после первого применения конфигурации»
- «Автоподбор ещё не запускался» + (Перепроверить сейчас) / «Добавьте цель»
- «Нет включённых правил с подключением» + (Добавить правило ›)

### J.5 Loading / timeout / error / stale

`AsyncBlock` — единая машина состояний для каждого асинхронного блока:

```
idle ─▶ loading ─▶ ready ─▶ (stale) ─▶ refreshing ─▶ ready
            │           └▶ empty
            ├▶ timeout (N с) ─▶ [Повторить]
            └▶ error ─▶ [Повторить] + ▸ Технические детали
forbidden (RO) — нейтральный текст, не ошибка
```

- **loading:** скелетон по высоте контента, без фиксированных 78 / 127px. После 3 с — «Всё ещё загружается…».
- **timeout:** «Роутер не ответил за 15 с» + Повторить. Для долгих операций (компоненты, автоподбор) — прогресс и время, а не таймаут.
- **error:** человеческий текст + Повторить + ▸ сырой текст ошибки.
- **stale:** данные старше 3 интервалов опроса → «Обновлено 2 мин назад», тон muted, данные не скрываются. **Сейчас stale-данные показываются молча** (Dashboard sections).
- **Инвалидация:** каждый запрос несёт generation-token. Ответ старого поколения отбрасывается: этот паттерн уже есть в `connectivityMatrix.ts:131-137`, его нужно обобщить. Все `try/finally` → `try/catch/finally` с переходом в `error`.
- **WS:** reconnect с backoff (1 → 2 → 5 → 10 с) и fallback на RPC poll после 3 неудач. На HTTPS — сразу RPC (или `wss`, если доступен).
