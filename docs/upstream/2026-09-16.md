## Selected changes

### Wait out a stale procd sing-box PID

`procd` can keep reporting an exited child for a few seconds after `/proc` no
longer holds any sing-box executable. Both controlled transitions treated that
as a foreign process:

- `stop_managed_sing_box_and_wait()` fell through to provenance resolution,
  which has no process to resolve, and logged "ownership is ambiguous before
  stop".
- `start_managed_sing_box_and_verify()` refused with "unexpected sing-box exists
  before start".

This fork is more exposed than upstream: 1.0.17 added the ownership gate to
`stop_main()` and moved the reload gate ahead of state capture, so a spurious
refusal propagates further. The package-upgrade path is where it is most
visible, which is the same area 1.0.17 and 1.0.18 already addressed.

The wait is bounded and stays fail-closed: a real sing-box appearing during the
wait still refuses the transition, the converged pair is confirmed twice because
the process scan and the ubus query are separate snapshots, and the reported PID
is never signalled since it may already have been reused.

`tests/singbox_stale_procd_pid.sh` covers the timeout, the converged case, and
asserts the wait contains no signalling.

## Not applicable

### FakeIP diagnostics runtime failure (`4478e192`)

Upstream introduced `fakeip_public_ip_comparison_available()` in `214e0fac` and
called it from `check_fakeip()`, which is declared above it. ucode compiles that
reference as a global load which the later declaration never satisfies, so the
FakeIP check raised a runtime error until `4478e192` reordered the helpers.

This is the same defect class this fork found and fixed on 2026-09-13 and now
guards with `tests/ucode_forward_reference.sh`. This fork does not carry
`fakeip_public_ip_comparison_available` at all, so neither the feature nor its
fix applies.

### owner_pid via /proc/self/stat (`b935d69f`, `9ea9c27e`, `69baf626`)

Upstream replaced `sh -c 'echo $PPID'` with a `/proc/self/stat` read, on the
grounds that the popen shell exits immediately and the recorded PID goes stale,
making LuCI expose Start during a running transition. The concern is real in
principle: this fork writes that PID into the reload lock, and
`acquire_runtime_dir_lock()` lets any caller steal a lock whose owner is dead.

Measured on the target platform before porting. On OpenWrt 25.12.5 with BusyBox
ash, the exact call form used here — `'sh' '-c' 'echo $PPID'` through
`fs.popen()` — returns the ucode process PID itself, and that PID is alive. The
shell `exec`s through both levels, so the reported owner is correct and the lock
cannot be stolen. Not imported: there is no defect to fix here, and rewriting
six call sites for an unreproduced failure is not worth the risk.

Part of `b935d69f` is the same declaration-order fix for `owner_pid_value()`
that this fork already applied on 2026-09-13.

### Manual restart latency cancellation (`5c63ef89`)

Guards `manual_restart()`, which this fork does not have. The accompanying
`generation` field belongs to upstream's latency rework, deferred since
2026-09-13.

### Connection-aware FakeIP comparison (`214e0fac`), test-only (`1d879f58`)

A diagnostics feature with a large frontend surface, not a fix for this fork.
Deferred.

## Preserved invariants

- Any otherwise valid HTTPS subscription provider remains supported; no upstream
  provider allowlist or automatic node-exclusion default is imported.
- Release ownership remains `slayer326/forkop`; `fold8.ru/forkop` distribution and
  `mirror.infotechtg.ru` dependencies are not replaced by upstream endpoints.
- Preserve exact managed PID/start-time transitions, transaction rollback and
  fail-closed ambiguity handling.
