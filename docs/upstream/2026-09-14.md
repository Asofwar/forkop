## Selected changes

### postinst waits for the previous sing-box to exit

`prerm` stops the service, but the sing-box child exits asynchronously.
`postinst` then called `/etc/init.d/forkop start` immediately, and this fork's
start refuses an ambiguous runtime by design — so an ordinary package upgrade
could leave Forkop stopped. Same user-visible symptom as the `prerm` action
defect fixed in 1.0.17, reached by a different path.

This fork is more exposed than upstream here: 1.0.17 also added the ownership
gate to `stop_main()`, and `start()` already refused on
`sing-box-process-conflict`. The existing `wait-managed-upgrade-sing-box-exit`
path does not cover this, because its marker is written only by the in-GUI
component updater (`components/action.uc`) and never by the package lifecycle.

The wait polls `/proc/<pid>/exe` for a binary named `sing-box` and never
signals anything. The scan root is env-overridable so the timeout and the
no-match paths are testable; `tests/package_upgrade_wait.sh` covers a clean
restore, a surviving process, and an unrelated process.

Upstream's own test for this is written to run on a router: it stops the live
service, copies `/usr/bin/ucode` and reads `/etc/config/forkop`. It was not
imported.

### Fallback sources for binary rule sets

`components/updates.uc` already falls back from the mirror to jsDelivr and
raw.githubusercontent for plain lists, but `singbox/ruleset_cache.uc` did not,
so a secondary `.srs` set resolved only through the mirror. The mirror outage of
2026-09-12..14 made that concrete, and a newly added set is missing from the
mirror until its next daily synchronization regardless.

Verified at the time of the port: `riot`, `sony` and `blizzard` answer 200 on
both the mirror and the CDN, while `twitch` is 200 on the CDN and 404 on the
mirror. The fallback therefore has to land together with the Twitch entry, or
the new option would be broken for every user until the mirror catches up.

### Twitch secondary ruleset

Added to the option list and to `CURRENT_SECONDARY_RULESET_IDS`. Consistent
with the extra built-in sets this fork already ships.

## Deferred changes and reasons

### Package upgrade quiesce, and everything built on it

`9c3ee635` and `c63f7eff` depend on `package-upgrade.quiesce`, which this fork
deliberately does not have (deferred on 2026-09-13). `c63f7eff` in particular is
purely a consumer of that marker — importing it alone would be dead code.

Upstream's quiesce work converged on the same conclusion this fork reached in
1.0.17, that opkg can omit the `prerm` action and every non-removal replacement
must be treated as an upgrade. It also pins the marker to the package-manager
parent PID, since a marker owned by the short-lived `prerm` process stops
quiescing the moment `prerm` exits. That detail is worth keeping if the marker
is ever adopted.

Importing it needs tests for a stale marker, a dead owner PID, and a worker that
starts between `prerm` and `postinst`.

### Component updater serialization

`wait_for_forkop_restore()` waits out a detached package start before deciding
whether to restart. It reads the quiesce state and the upgrade marker together,
so it follows the same deferral.

## Preserved invariants

- Any otherwise valid HTTPS subscription provider remains supported; no upstream
  provider allowlist or automatic node-exclusion default is imported.
- Release ownership remains `slayer326/forkop`; `fold8.ru/forkop` distribution and
  `mirror.infotechtg.ru` dependencies are not replaced by upstream endpoints.
- Preserve exact managed PID/start-time transitions, transaction rollback and
  fail-closed ambiguity handling.
- No production-router installation is authorized by this source audit. Hardware
  validation, when absent, must be disclosed.
