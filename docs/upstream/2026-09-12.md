## Selected changes

### Bootstrap DNS for remote lists and rule sets

Remote domain/subnet lists and sing-box rule sets can retry a direct download
through a configured Bootstrap DNS server when curl reports name-resolution
failure (exit code 6). This extends the subscription-download fallback already
present in 1.0.15.

The adaptation retains download size/free-space limits, last-known-good cache,
atomic application and sanitized logging. DNS lookup is bounded, IPv4/IPv6
answers are parsed without confusing the DNS server address with the answer,
and an explicit proxy is not bypassed. The HTTPS hostname remains unchanged:
`curl --resolve` supplies its address without disabling certificate checks.

### Correct URL authority parsing

`core/url.uc` now determines where the authority ends before interpreting `@`
as a user-information delimiter. An `@` in a path, query or fragment must not
change the hostname. Actual authority user information and explicit ports still
need to parse correctly. This matters to subscription/list hosts and Bootstrap
DNS resolution; it does not restrict the accepted subscription providers.

### Priority card disclosure state

Priority membership is collapsed initially and the user's expand/collapse
choice survives dashboard refreshes for that card. State is keyed by section
and outbound, rather than by a transient DOM node. The LuCI adaptation omits
the boolean `open` attribute for a collapsed card, instead of rendering
`open="false"`, which HTML still treats as open.

### Installed sing-box package reporting

Diagnostics and capability detection identify the exact installed package
(`sing-box`, `sing-box-tiny`, `sing-box-extended`) and give package-manager state
precedence over a stale variant marker. This avoids presenting an ordinary
package as Tiny/Extended after a manual package replacement. Package identity
does not weaken the separate managed-process ownership checks.

## Deferred changes and reasons

### New DNS watchdog

Do not import `service/watchdog.uc` or its procd instance unchanged.

The upstream watchdog treats failure of `sing-box-single-owned-service-runtime`
as an outage, including the case where an unrelated or second sing-box process
exists. It later calls bare `forkop stop` without atomically acquiring the
reload lock. Checking whether the directory exists earlier in the polling loop
does not serialize that stop with a subsequent start/reload.

In this fork, `stop_main()` removes the nftables policy before the controlled
sing-box stop rejects ambiguous ownership. An automatic stop in that situation
could discard the fail-closed policy while the unknown process remains alive.
The 90-second startup grace and 60-second failure delay do not remove this race.

Reference: [upstream watchdog](https://github.com/Screamshow/forkop/blob/ad17cda18ff06b43a9323fd1523ec0685aba63a4/forkop/files/usr/lib/service/watchdog.uc#L33).

A future watchdog needs distinct missing/ambiguous/transitioning states, atomic
coordination, and explicit handling of the fork's legacy DNS restoration and
fail-closed routing contract. Required tests include PID reuse, foreign and
duplicate processes, stale/live locks, concurrent reload, failed rollback and
DNS restoration after a confirmed missing managed process.

### Post-start latency barrier and reload resumption

The goal is useful: measure only the final proxy set after the startup
list/rule-set pipeline. However, the new hooks are interdependent and source
review found two uncovered execution paths:

1. During a batched latency test, the old worker retains the latency lock while
   synchronously handing a pending reload off. Reload completion launches a
   replacement worker. That replacement can see the old lock and coalesce its
   request before the old worker releases it. The old worker then observes the
   changed sing-box PID and does not launch another replacement because it
   assumes the pending reload already did so. A marker can remain without a
   worker. See [batch handoff](https://github.com/Screamshow/forkop/blob/ad17cda18ff06b43a9323fd1523ec0685aba63a4/forkop/files/usr/lib/diagnostics/runtime.uc#L1962)
   and [reload scheduling](https://github.com/Screamshow/forkop/blob/ad17cda18ff06b43a9323fd1523ec0685aba63a4/forkop/files/usr/lib/service/lifecycle.uc#L505).
2. Startup writes `post-start-latency.pending` when list sources exist. If the
   list worker refreshes rule sets inline and both generations are unchanged,
   `finish_list_update()` exits without a runtime reload or a post-start
   completion callback. The new callback exists in the standalone rule-set
   worker path, not this no-change path. The barrier can therefore remain
   without scheduling latency. See [list completion](https://github.com/Screamshow/forkop/blob/ad17cda18ff06b43a9323fd1523ec0685aba63a4/forkop/files/usr/lib/components/updates.uc#L3744)
   and [standalone callback](https://github.com/Screamshow/forkop/blob/ad17cda18ff06b43a9323fd1523ec0685aba63a4/forkop/files/usr/lib/singbox/ruleset_cache.uc#L682).

These are code-review findings, not claims of reproduced failures on a physical
router. Upstream's added serialization assertions primarily check source
strings and do not establish either concurrency ordering. Retain the existing
latency/reload behavior for this release. A later adaptation needs deterministic
handoff tests plus no-change, download-failure, queued-reload and rollback-failure
completion tests before replacing that lifecycle.

### Cold-boot rule-set reload

The upstream `manifest_has_entries()` fallback can request a reload even when
the cached generation is fresh and unchanged. Its intended benefit is replacing
an empty startup fallback, but manifest presence alone does not prove the live
configuration references that fallback. It also participates in the deferred
latency pipeline above. Do not introduce an unconditional reload based only on
cache presence; first test whether runtime materialization is actually missing.

### Full uninstall and release channels

Additional full-uninstall cleanup is intentionally destructive and is not
required for this update. Do not expand removal of packages, configuration or
TorrServer Direct state as part of a routine stability port.

Upstream stable/canary selection is not needed by the fork's existing release
distribution. Do not import it or switch update metadata endpoints implicitly.

## Follow-up audit: 2026-09-13

Also reviewed release 1.3.15 (`0c7e523c`) and subsequent commits through
`3cedbce8133c216d2eb980172e6750342c1b1fc9`.

- Ported the idempotent duplicate-start check. It runs after managed-upgrade
  provenance and process-conflict guards and accepts only the full existing
  `forkop-stably-running` predicate (sole owned process, stable age, listeners,
  Clash API and routing/nftables state). Partial or ambiguous runtime is not
  silently adopted. A retained `forkop_transition_guard` after failed rollback
  also prevents a false success and is left intact. The new deterministic test executes the real start and
  stable-predicate functions with controlled dependencies.
- Ported automatic retry outcome logging without changing its start/stop
  behavior or exit status.
- Deferred the new UI startup-error suppression: the upstream notification
  controller stores a recoverable fatal line in `pendingFailure` but never
  flushes it if no retry event follows. This can hide a real startup failure.
- Deferred the narrower automatic latency candidate filter. A valid group-only
  configuration can produce zero independent candidates, while the unchanged
  worker treats that as failure and leaves a retry marker. The no-selector
  fallback can also include detached nodes. A future adaptation needs a
  successful no-work path and group-only/no-selector/mixed-membership tests.

[Follow-up source changes](https://github.com/Screamshow/forkop/compare/ad17cda18ff06b43a9323fd1523ec0685aba63a4...3cedbce8133c216d2eb980172e6750342c1b1fc9).

### Additional fork-specific corrections

Bootstrap DNS accepts a validated address even when BusyBox's second A/AAAA
query fails; stdout is limited to 16 KiB and nslookup uses a five-second timeout.
Regular sing-box packages still use the existing bounded/cached build-tag probe
to detect Tailscale, while active component replacement prevents live probing.

The pre-download DNS probe distinguishes a *configured* Bootstrap server from a
*reachable* one. The shipped default config always lists a Bootstrap server, so
treating configuration alone as sufficient would have removed the cold-boot
grace period for every install: the first failed system lookup would return
success, and `list-update-after-start` on a router whose WAN has not finished
coming up would exhaust its three download attempts and wait for the next cron
run — up to a day at the default interval. The probe now continues only when a
configured Bootstrap server actually answers, and otherwise keeps the original
ten-attempt wait. Bootstrap is probed on the first and the last attempt only,
so the worker's hold on the reload lock stays bounded.

- Any otherwise valid HTTPS subscription provider remains supported; no upstream
  provider allowlist or automatic node-exclusion default is imported.
- Release ownership remains `slayer326/forkop`; `fold8.ru/forkop` distribution and
  `mirror.infotechtg.ru` dependencies are not replaced by upstream endpoints.
- No new active `mirror.51343.ru` dependency. Legacy migration/detection strings
  may remain where they are required to restore previous installations safely.
- Preserve exact managed PID/start-time transitions, last-working subscription
  and list generations, transaction rollback and fail-closed ambiguity handling.
- No production-router installation or shared VPS service restart is authorized
  by this source audit. Hardware validation, when absent, must be disclosed.
